DECISIONS THAT WOULD NOT BE OBVIOUS
-----------------------------------
1. Escrow is enforced in two layers, deliberately.
   - src/lib/escrow/machine.ts is PURE: the legal-move table, actor
     entitlement, required reasons. No DB, so it is exhaustively unit-testable
     with no Docker. machine.test.ts hard-codes the eight documented moves
     separately so the table cannot drift silently.
   - askr.apply_order_transition() is the atomic tail: SELECT ... FOR UPDATE,
     re-check the from-state, UPDATE orders, INSERT order_events, one
     transaction. The orders_state_guard trigger raises on any other UPDATE,
     including from the service role.
   - order_events has a BEFORE UPDATE OR DELETE trigger that always raises.
     Append-only is enforced at the table, not RLS, because RLS does not apply
     to the service role.

2. Money model. Buyer pays the quote plus a 5% platform fee
   (COMMISSION_BPS = 500). On release the platform keeps that fee as commission
   and the provider receives exactly what they quoted, so
   commission_cents === platform_fee_cents. Reproduces the mockup's
   $170.00 / $8.50 / $178.50.

3. request_broadcasts is both the notification log and the RLS predicate. A
   provider can read a request because a row links them to it — which is why
   private requests need no second mechanism, and why only the service role may
   write that table.

4. No counter-offers (Phase 2). The partial unique index
   offers_one_active_per_provider WHERE status='active' is what makes
   withdraw-and-re-offer the negotiation mechanism instead.

5. Admin is not self-assignable. handle_new_user() maps signup metadata to
   buyer/provider only; seed.sql promotes the one admin with a direct UPDATE.
   guard_provider_self_service() strips verification_status, rating fields and
   stripe_account_id from any non-admin update.

6. Geo is a plain haversine SQL function (askr.distance_km), not PostGIS.
   Matching needs BOTH radii to hold: the provider will travel that far AND the
   buyer will look that far. One-sided matching fails in both directions.
   No geocoder in Phase 1 — buyers pick from src/lib/nz-locations.ts, which
   carries the coordinates. Swapping in a geocoder changes only that file.

7. Auth failures are deliberately vague, and the magic-link form returns the
   same notice whether or not the address exists. Distinguishing "no such
   account" from "wrong password" enumerates registered emails.

8. Best match uses a 0.15 rating band, calibrated against the mockup's own
   stack (4.9/$170, 4.8/$160, 5.0/$190, badge on the 4.9). A 0.2 band pulls the
   4.8 in and the badge moves to the cheaper offer; no band at all moves it to
   the dearest. The band is what separates "near-identical rating, take the
   cheaper" from "genuinely better rated, worth the money". A provider with no
   ratings can never be best match — they have no rating to compare.


DEPLOYMENT
----------
Target: Vercel + hosted Supabase. Tables live in schema `askr`, NOT public.

Two settings that silently break everything if missed:
  * Supabase > Project Settings > API > Exposed schemas must include `askr`.
    Without it every query returns "The schema must be one of the following".
  * The supabase-js clients pass { db: { schema: "askr" } }. Any new client
    must do the same or it queries public and finds nothing.

Custom schemas get none of the grants Supabase applies to public, which is why
20260809000050_schema.sql sets usage + default privileges and
20260809000400_grants.sql re-applies them explicitly after the tables exist.
apply_order_transition and match_providers have EXECUTE revoked from
anon/authenticated — both are service-role operations.

Realtime: OfferStack subscribes to postgres_changes on schema `askr`, table
`offers`. The publication is set up in 20260809000100_schema.sql; confirm the
four tables are listed after the first push.

Vercel env vars: NEXT_PUBLIC_SUPABASE_URL, NEXT_PUBLIC_SUPABASE_ANON_KEY,
SUPABASE_SERVICE_ROLE_KEY, STRIPE_SECRET_KEY,
NEXT_PUBLIC_STRIPE_PUBLISHABLE_KEY, STRIPE_WEBHOOK_SECRET, NEXT_PUBLIC_SITE_URL.


ENVIRONMENT NOTE
----------------
This machine has no Docker and no Supabase CLI, so NONE of the SQL has ever
been executed. Six migrations, ~1000 lines, unverified against a live Postgres.
This is the largest untested risk in the repo. `./init.sh local` (Docker) or
`./init.sh hosted` (linked project) applies them; expect to fix errors on the
first run.

Node 26.4.0 / npm 11.17.0. npm 11 gates install scripts: if esbuild or
unrs-resolver report missing binaries, run
`npm approve-scripts esbuild unrs-resolver`.

fact-forcing hook, which otherwise blocks every file write in this build.
